# SDD team-lead playbook — Resume

Part of the team-lead playbook (`team-lead.md` holds §0–§2, §11 and §12 and says where every other section lives). Read when `/sdd` resumes a live run (§1 step 6).

## 13. Resume

You have already run `doctor.mjs` (§1 step 4) and the user chose to resume. Read the lane's file (`quick.md` or `full.md`) and, from `executing` on, `execution.md`.

If the marker has `stop`, handle it per §10 (`stops.md`) before anything else (re-show the options if `choice` is null). Resume state is exactly: the marker, the spec `status:` value, the plan task checklist, and the review records in `.sdd/review/`. Never restart a completed stage. If the marker has `amendment`, resume under §9 (step 7, `amendments.md`) instead of the entries below. Otherwise continue at the recorded `stage`:

- `spec-draft`: re-dispatch the analyst (§4); if the spec already has review records, the user had asked for changes at the approval gate (§4 step 4): ask them to restate the changes and relay those instead. `spec-review` / `plan-review`: re-enter §5 with the round counter and the rejected list rebuilt from `.sdd/review/<slug>-<artifact>-r*.md` (the highest-numbered record's first line gives the loop and round and its last `Exit:` line says whether to run the next round or the loop had ended; the rejected list = every `rejected:` disposition in every record of the artifact, across all loops — see §5). When that `Exit:` is `clean` or `new loop` while the stage is still the review stage, start a new loop (a revision requested at the approval gate may not have been reviewed yet; at worst this repeats a review that had just ended clean). `spec-approval` / `plan-approval`: ask for approval again.
- `outline-draft`: if records with `scope outline` already exist, the user had asked for changes at the outline gate (§6 step 3): ask them to restate the changes and relay those (an OUTLINE revision) instead; otherwise, when the manifest exists and `node "<kit>/bin/plan.mjs" check "<manifest>" --outline --spec "<spec>"` prints `ok`, continue at §6 step 3, and when it does not, re-dispatch the planner in OUTLINE mode (§6 step 1). `outline-review` / `outline-approval`: as `spec-review` / `spec-approval`, for the outline (§6 step 3).
- `plan-draft`: a marker with no `slice` is a legacy run: continue at §14 (`legacy.md`) when the plan file exists, and restart at §6 step 1 as a 0.3 plan when it does not (a 0.2 run cut during planning). With a `slice`: if records with `scope slice <n>` (`scope plan` for a single-slice plan) exist for the current slice, the user had asked for changes at the approval gate (§6 step 7): ask them to restate the changes and relay those instead of anything below; otherwise run `node "<kit>/bin/plan.mjs" tasks "<manifest>"` and continue §6 step 4 at the first task of the current slice that is not expanded (never re-dispatch a task whose file exists, and never the whole plan), and when every task of the slice is expanded continue at §6 step 5.
- `executing`: continue §7; a task whose `in_progress` is `true` was interrupted — re-dispatch it as an **FF dispatch** at its recorded `attempt_tier` (§7.3 "Lost attempts": route with `--resume <key> --record <key>`), leaving `last_tier` and `failures_at_last_tier` unchanged (a lost attempt does not count as a failure).
- `code-review` / `review-fix`: continue §8; fix rounds used = the number of `.sdd/review/<slug>-code-r*.md` records minus one.
- QUICK stages: continue §3, using `.sdd/review/<slug>-code-r1.md` if it exists.
