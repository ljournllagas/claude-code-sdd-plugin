# SDD team-lead playbook — Execution

Part of the team-lead playbook (`team-lead.md` holds §0–§2, §11 and §12 and says where every other section lives). Read before the first developer dispatch of a run: FULL uses all of §7, QUICK uses the attempt procedure (§7.3).

## 7. Execution (FULL)

### 7.1 Entering `executing` for the first time

Make the status edit of the plan to `executing` (only when it is not already `executing`) and the marker `stage: "executing"`. Then, the first time only (`base` is still `null`), in this order:

1. Record `dirty_at_start` in the marker: `marker.mjs baseline --dirty` (the changed paths of `git status --porcelain --untracked-files=all`; empty list when not a git repository).
2. **Pre-flight.** `marker.mjs preflight <manifest> --slice <n>` (every task, for a legacy plan: `--tasks <all IDs>`). Exit 1 lists the task Files paths that carry uncommitted changes: stop with §10 "Dirty-files pre-flight". On **Ready**, re-record `dirty_at_start` (`baseline --dirty`) and re-check.
3. Record `base`: `marker.mjs baseline --base` (`git rev-parse HEAD`, or `none` if it fails: not a git repository, or a repository with no commits yet; the final review then uses the file list, §12.4).

`base` and `dirty_at_start` are **never re-recorded** afterwards: re-entering `executing` after an amendment, after a slice approval (§6 step 8) or on resume leaves them untouched; at the start of each later slice run the step 2 pre-flight for that slice's tasks only. Before `executing` both are `null`. Paths in `dirty_at_start` that are outside every task's Files list are noted to the user once and the run continues; per-task commits stage only the task's Files list, so unrelated changes are never committed. In a non-git project make no commits and say so once.

### 7.2 Task order

Run the tasks of the current slice (all tasks, for a legacy plan) one at a time in dependency order (a task whose dependencies are all `[x]`), skipping `[x]` tasks and any task marked `[!]`. A `Manual:` task (its Verify line reads `Verify: Manual: <steps>`) is executed like any other and then verified by the user (§10 "Verify set empty or a Manual task"). Never dispatch a task of a slice that is not in `approved_slices` (a legacy run, whose marker has no `slice`, is exempt). When no pending task of the current slice remains: if a later slice exists go to §6 step 8, otherwise set `stage: "code-review"` and go to §8.

### 7.3 The attempt procedure (task key = the task ID, or `quick` / `quick-fix` in QUICK)

1. **Route.** Build the developer card (§12.1). On the first attempt there is no `last_tier`. After a failed attempt use the decision returned by step 8 directly — it already is the routing for the next attempt, so do not route twice. If the task is pending (QUICK: not yet verified) and already has a `tasks` entry with `in_progress: false` (a session was lost after an attempt): when its failure file does not exist, the latest attempt was never verified — run step 7 first; when it exists, route with `--retry <key>` (not as a first attempt) and apply the decision as in step 8 — but if the entry has no `last_tier` (the session was lost after the failure file was written but before step 8 saved the counters), run step 8 in full instead. If `human: true` → §10 "Task needs a human".
2. **Record.** The entry `tasks[key] = {attempt_tier: <decision.tier>, last_tier, failures_at_last_tier, in_progress: true, routed: {source: <decision.source>, reason: <decision.reason>}}` (no `last_tier`/`failures_at_last_tier` before the first failure) is written by the routing call's `--record <key>` (§12.1), which also refreshes `updated`. Every developer dispatch goes through this write, including the QUICK `quick-fix` dispatch (§3 step 6); no other write changes `routed`.
3. **FF dispatch?** The dispatch is an **FF dispatch** (fix-forward) when it is a retry or escalation, a resume re-dispatch, or the task's Files list overlaps any path `git status --porcelain --untracked-files=all` currently shows as changed (excluding run artifacts). You never restore or delete files automatically. An FF dispatch prompt carries the `FF DISPATCH` line of §12.2: it states which paths already carry edits, includes the failure file path when one exists, and waives the Red check.
4. **Dispatch** a **fresh developer** (§12.2). It receives only that task's block (a split plan: the task file path; a legacy plan: the plan path and the task ID), the Verify commands, the runner line, and on a retry the failure evidence. Never resume a finished developer.
5. **Set `in_progress: false`** after the attempt returns (or is lost): `marker.mjs set tasks.<key>.in_progress=false`. Then delete the task's failure file under `.sdd/review/` if one exists (a run artifact; it has served as this attempt's evidence), so that it exists only when the latest attempt failed.
6. **Interpret the return.**
   - `TASK-BLOCKED: design-gap — …`: not verified, and not a failure. Mark the task `[!] blocked`, write its **Outcome line** (`blocked`), apply §10 "Leftover edits", then stop executing tasks and route the finding to the planner as an amendment (§9).
   - `TASK-BLOCKED: defect|environment — …`: not verified. Its message is the failure evidence: write it to the failure file, then its **Outcome line** (`fail`). It counts as a failed attempt (go to step 8).
   - `TASK-DONE`, or no usable report: continue to step 7.
7. **Verify** — run the task's Verify with `verify.mjs --manifest <manifest> --task <T-id> --key <T-id>` (§12.3) whether or not a report came back. For a `Manual:` task (exit 4) ask the user instead (§10 "Verify set empty or a Manual task"). Then:
   - **Success:** run `node "<kit>/bin/task-done.mjs" --manifest <manifest> --task <T-id> --duration-ms <n> --agent-tokens <n>` (the `<usage>` figures; omit a flag whose figure is absent). It marks the task `[x] done` (single-line replacement); in a git project it (i) checks for changed or untracked paths outside the task's Files list (minus `dirty_at_start`, `kept`, run artifacts and the Files of tasks already marked `[x]`) and, if any exist, lists them as `leftover:` lines and exits 3 having committed nothing: apply §10 "Leftover edits" (**Keep** adds them to the run paths), then run the same command again; (ii) commits only the files in the task's Files list that exist, with the task's `Commit:` line as the message (`git add -- <those paths>` then `git commit -m "<the task's Commit line>" -- <those paths>`), dropping a listed path that does not exist from the pathspec and naming it, and skipping the commit only when none of the listed paths changed; then it refreshes `updated` and writes the task's **Outcome line** (`pass`). Keep its one-line output as the task's summary for the report, then take the next task. Exit 5 (`commit failed: …`, for example a commit hook refused) is shown to the user verbatim; stop and wait.
   - **Failure:** `verify.mjs` has written the last 40 lines of failed output to `.sdd/review/<slug>-<task>.fail.txt`; write the task's **Outcome line** (`fail`) and go to step 8.
8. **Count and re-route.** Every failed attempt — a failed verify, a `TASK-BLOCKED` defect/environment, or an attempt that ended with no report and then fails verify — **increments** `failures_at_last_tier` (setting `last_tier` to the attempted tier if absent): `marker.mjs fail <key>`, which writes the incremented counters to the marker **before** you route. Then route the developer card with `--retry <key> --record <key>` (§12.1): the card carries `last_tier` and `failures_at_last_tier`, and when the decision's tier is higher than `last_tier`, the record sets `last_tier` to the new tier and `failures_at_last_tier` to 0. If `human: true` → §10 "Task needs a human" (nothing was recorded). Otherwise return to step 3 with that decision (step 2's write is done).

**Lost attempts.** An attempt lost to session loss **does not increment** `failures_at_last_tier`. On resume, an entry whose `in_progress` is still `true` — for any task key: a plan task ID, `quick` or `quick-fix` — is re-dispatched as an FF dispatch at its recorded `attempt_tier`, with `last_tier` and `failures_at_last_tier` left exactly as recorded: route with `--resume <key> --record <key>`, whose card carries `last_tier` = that `attempt_tier` and `failures_at_last_tier` = the recorded count (0 if absent), which returns that same tier without a network call, then continue at step 3. If the decision differs (the config changed between sessions) or has `human: true`, follow it as in step 8.

**Outcome line.** When an attempt reaches a verdict, record it from the project root: a FULL `pass` is written by `task-done.mjs`; every other verdict by `node "<kit>/bin/outcome.mjs" --from-marker --task "<key>" --result <pass|fail|blocked> [--duration-ms <n>] [--agent-tokens <n>]`. `--from-marker` takes the values from the marker's `tasks[key]` entry, never from memory of the conversation: the tier is `attempt_tier`; the source and reason are `routed.source` and `routed.reason`; `first_attempt` is `true` exactly when the entry has no `last_tier` at that moment (write the line before step 8's `marker.mjs fail`, which is what sets `last_tier`; a retry or an escalation is therefore `false`, a lost attempt re-dispatched is still `true`, and a replaced task whose entry was deleted is `true` again). `--duration-ms` and `--agent-tokens` are the `duration_ms` and `subagent_tokens` figures of the `<usage>` block that ends the dispatch result; omit a flag when that figure is absent (a verify re-run in a new session has no dispatch). (Should you ever give the values as flags yourself, double-quote the `--reason` value: router reasons contain `<`, `(`, `)` and `;`.) The script appends one line, with `kind: "outcome"` and a `first_attempt` field, to the decision log. Rules:
- **Result.** A verify command passing is `pass`; a verify command failing, or `TASK-BLOCKED: defect|environment`, is `fail`; `TASK-BLOCKED: design-gap` is `blocked`. A user's answer never produces a line: a `Manual:` task, or a QUICK run with an empty verify set, that the user confirms or rejects writes none.
- **Whose verdict.** A human fix is not a developer attempt: the verify that follows §10 "I fixed it" writes no line (`task-done.mjs --no-outcome`), nor does a task that is skipped, aborted or stopped by `human: true`, nor an attempt lost to a session cut. A session that resumes into a stage, or carries out a recorded `stop.choice` (§10), never writes a line for a verdict reached before the cut; only the session that itself sees the verify result or the `TASK-BLOCKED` return writes it.
- **When.** After the durable record of the verdict, and in no case before it: a FULL `pass` after the `[x] done` edit and the commit (`task-done.mjs` keeps that order, also when its first run stopped on leftover edits); a QUICK `quick` pass after `stage` is set to `quick-review` (§3 step 5); a QUICK `quick-fix` pass right after its verify set passes, before §3 step 7; a `fail` after the failure file is written and before step 8; a `blocked` after the `[!] blocked` edit (QUICK: at the start of §3 step 4's design-gap handling) and before §10 "Leftover edits", because §9 step 5 deletes the entry that holds `routed`.
- **No `routed`.** An entry written by an older Kit has none: no line is written for that attempt (the scripts skip it with a warning).
- **Never blocks.** Exit code 2 means your invocation was malformed: correct it and retry once. Any other warning goes in your next status line and the run continues. Logging never changes the run.

A developer that edits files outside the task's Files list has broken its contract: step 7 (i) catches it on success and the user decides under "Leftover edits"; mention it in the report as a possible plan defect (an incomplete Files list).
