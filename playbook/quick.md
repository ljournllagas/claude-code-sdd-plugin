# SDD team-lead playbook — Lane QUICK

Part of the team-lead playbook (`team-lead.md` holds §0–§2, §11 and §12 and says where every other section lives). Read on a QUICK run, together with `execution.md` (§7.3, the attempt procedure).

## 3. Lane QUICK

No spec, no plan, no commit. Counters live in `tasks.quick`; the single review fix uses `tasks.quick-fix`.

1. **Baseline.** Set `stage: "quick-dev"` and record the baseline in one go: `marker.mjs set stage=quick-dev` then `marker.mjs baseline`. It records `base` = `git rev-parse HEAD` (`none` if it fails: not a git repository, or a repository with no commits yet; the review then uses the file list, §12.4) and `dirty_at_start` = the changed paths of `git status --porcelain --untracked-files=all` (empty list when not git).
2. **QUICK verify set** = every non-null command among `cfg.verify.build`, `test`, `lint`, `typecheck` (**never format**), in that order, stopping at the first failure; `verify.mjs --quick` runs exactly this set (§12.3). If all four are null (it prints `empty:`), say so: there is nothing to run, and the user must confirm the result manually (§10 "Verify set empty").
3. **Brief.** Write no artifact. The brief goes in the dispatch prompt only (§12.2): the request restated as a goal, the paths you expect to be touched (best effort: the triage paths), the QUICK verify set, and the instruction that `TASK-BLOCKED` is the answer to any decision the brief does not settle. Tell the developer to add or update tests when `cfg.verify.test` is non-null.
4. **Attempt loop.** Read `execution.md` and run the attempt procedure of §7.3 for task key `quick` with these differences: the card is the QUICK developer card (§12.1); "the task's Verify" is the QUICK verify set (`verify.mjs --quick --key quick`); there is no plan marker to update, no commit, no `task-done.mjs` and no per-task leftover check (leftover edits are handled at the end, in step 7 below). A failed verify follows the same escalation ladder and the FF rule as FULL tasks. QUICK has no plan to amend, so a `TASK-BLOCKED: design-gap` is handled differently from §7.3 step 6: first write its **Outcome line** (`blocked`, §7.3), then apply §10 "Leftover edits", show the developer's message to the user and stop; the user's next message is treated as a restated request (re-triage, §2) or they end the run.
5. **Review.** Set `stage: "quick-review"`; the QUICK `pass` **Outcome line** (§7.3: `outcome.mjs --from-marker --task quick --result pass`) is written right after that write, only by the session that saw the verify pass (a session resuming at `quick-review` writes none). Build the **run diff** (§12.4) over the QUICK run paths and write it under `.sdd/review/`. Route stage `reviewer-code` and dispatch the reviewer with `MODE: code` and `Goal: <the brief's goal>` (§12.2), so it can judge whether the change does what was asked. A return with neither findings nor a Verdict is *did not review*, never a pass (the §5 step 2 rule): re-dispatch once; if it is still empty, write no record, note "unreviewed" for the report and go to step 7. Otherwise write the record `.sdd/review/<slug>-code-r1.md`: the reviewer's whole return, copied unchanged from its `## Review —` line (never summarised or reworded), then a `## Dispositions` section with one line per blocker, `fix` or `rejected: <one-line reason>`, triaged as in §5 step 4. If any run path is also in `dirty_at_start`, note that the diff for that path includes the user's earlier edits, and repeat this in the report.
6. **Review blockers.** Only if at least one blocker is marked `fix`, one fix round is allowed: set `stage: "quick-fix"`; route a developer card (summary "fix review blockers", `--record quick-fix`, so that `routed` is recorded as §7.3 step 2 requires), and dispatch it as an **FF dispatch** (§7.3 step 3) carrying the path of the review record, to fix only the blockers marked `fix`; re-run the QUICK verify set (`--key quick-fix`; same ladder, counters in `tasks.quick-fix`, and the §7.3 **Outcome line** for its verdict, written before step 7); **no second review**. With no blocker marked `fix`, go to step 7. Anything still open, and every rejected blocker with its reason, is listed verbatim in the report.
7. **Finish.** If an attempt's edits remain and no further attempt follows (ladder exhausted, `human:true` → Abort; QUICK offers no Skip, only I fixed it / Retry at deep with guidance / Abort), apply §10 "Leftover edits" first. Then §11 (report). The changes stay **uncommitted** in the working tree.
