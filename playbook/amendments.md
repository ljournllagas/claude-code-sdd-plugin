# SDD team-lead playbook — Amendments

Part of the team-lead playbook (`team-lead.md` holds §0–§2, §11 and §12 and says where every other section lives). Read at the first amendment of a run: a design-gap `TASK-BLOCKED`, review fix tasks, or a `SPEC-GAP` / `OUTLINE-GAP` from the planner.

## 9. Amendments after approval

Applies to: a design-gap `TASK-BLOCKED`, review fix tasks, and a spec gap found by the planner (`SPEC-GAP`, after the user's **Decide** at §10 "Spec gap": the analyst's dispatch carries the finding and the user's decision verbatim).

1. **Amendment:** write (with `marker.mjs set`) `amendment: {artifact: "spec"|"plan", blocks: <task IDs or sections to change>, return_stage: "executing"|"review-fix"|"outline-draft"|"plan-draft"}` to the marker (`review-fix` for fix tasks; for a `SPEC-GAP` or `OUTLINE-GAP` raised while a plan is first being written, `outline-draft` when it came from the outline (§6 steps 1-3) and `plan-draft` when it came from expanding a slice (§6 step 4), with step 4 of this section skipped (the plan is not yet approved, so there is nothing to set back to `draft`) and §6 resuming at that step; when the planner appends fix tasks, set `blocks` to their IDs once it returns) and set `stage` to `plan-draft` (`spec-draft` for a spec change). Then the authoring agent writes the change (planner for plan content, analyst for the spec), routed, with the finding and the artifact path. You never edit the content yourself.
2. The reviewer checks **only the amended blocks** under the §5 loop rules as a **new loop** (fresh round cap and stall comparison, the artifact's full rejected list): the reviewer prompt carries `Review only these blocks: <blocks>`. While it runs, `stage` is `plan-review` (`spec-review` for a spec change).
3. The user approves the amendment before any changed task runs (a user message that approves; never inferred). While you wait, `stage` is `plan-approval` (`spec-approval`). Once the last approval is given (for a spec change, after step 4), remove `amendment` from the marker and set `stage` to its `return_stage`.
4. A **spec** change after approval sets the plan's `status:` to `draft` (a status edit), and the planner revises only the affected tasks before execution resumes: set `amendment` to `{artifact: "plan", blocks: <the affected task IDs>, return_stage}` and `stage: "plan-draft"` while it revises, then plan amendment review (`plan-review`) and approval (`plan-approval`) as above, and `status: executing` again without re-recording `base`/`dirty_at_start`. Completed tasks that are unaffected are not redone.
5. An amended or replacement task keeps its ID but is a **new task for routing**: delete its `tasks` entry (`marker.mjs del tasks.<id>`; counters reset, `last_tier` absent) and route it fresh. Reset its heading marker to `[ ] pending`, and likewise every task marked `[!] blocked` only because of it.
6. Before any amended or fix task runs, re-run the pre-flight of §7.1 for that task's Files list against the current `git status --porcelain --untracked-files=all` (excluding leftover edits the user chose to **Keep**): `marker.mjs preflight <manifest> --tasks <its IDs>`, with `base` and `dirty_at_start` unchanged.
7. **Resume.** While the marker has `amendment`, the stages `spec-draft`, `spec-review`, `spec-approval`, `plan-draft`, `plan-review` and `plan-approval` resume at the matching step of this section, not at the entry steps of §4, §6 step 1, 4 or 7: never re-write the whole spec or plan (the author is dispatched only to revise `blocks`); the reviewer prompt carries `Review only these blocks: <blocks>`; at a review stage, an open `stop` in the marker is handled first (§13, §10) — a record ending `Exit: stall` or `Exit: cap hit` with that stop open never starts a new loop; otherwise §5's resume rules apply, except that when the artifact's highest-numbered record has an `Exit:` line other than `next round`, no round of this amendment's loop is in progress, so a new loop starts (at worst this repeats a review that had just ended clean); approval stages ask for approval of the amendment again and then continue as in step 3 or 4.
8. **Split plans.** `blocks` are task IDs (or `manifest`). The planner rewrites each amended task file whole and appends a fix task as a new file `T<next>.md` plus an `Edit` of the manifest (index entry in the current slice, `**Task count:**`, coverage matrix row), so a fix task never rewrites the plan. A change that touches tasks of another, not yet executed slice is a manifest amendment: `blocks` = `manifest`, reviewed with `Scope: outline`, user-approved like any amendment; the affected slices are expanded afterwards as usual. A slice that has been executed is never re-planned: the changes it needs are fix tasks in the current slice. A reset task marker (step 5) is an edit of that task's own file. After a manifest amendment set `slice.total` in the marker to the manifest's number of slices (`plan.mjs tasks`), so that §6 step 8 still reaches an added slice.
9. **Mechanical check after an amendment.** After every planner dispatch that amends or adds tasks, run `node "<kit>/bin/plan.mjs" check "<manifest>" --slice <n> --spec "<spec>" --paths` (`--plan` for a single-slice or legacy plan, `--outline` after a manifest amendment) and, on defects, re-dispatch the planner once (routed, "revise: plan defects", the defect lines in the prompt), then apply §10 "Plan check failed". The review of the amended blocks (step 2) follows a clean check.
